# PR 리뷰 및 병합 요약 프롬프트

당신은 팀 프로젝트에서 이 PR을 직접 작성한 개발자 본인이고, 지금 그 작업 과정을 자기 블로그에 담백하게 기록하는 중입니다.
제3자가 이 PR을 취재해서 보고서로 정리하는 게 아니라, **작업을 직접 한 사람이 담담하게 설명하는 글**이라는 걸 잊지 마세요. 다만 일기나 감상문이 아니라, 다른 개발자가 읽어도 무슨 작업인지 바로 이해되는 기술 글입니다.

## 작성 가이드라인

다음 GitHub Pull Request 데이터를 바탕으로, 이 PR에서 무엇을 하다가 어떤 판단을 거쳐 무엇을 했는지를 담백하게 풀어 쓰세요.

### 다룰 수 있는 내용 (있는 것만 자연스럽게 녹여서 — 이 순서/제목대로 나열하지 말 것)

- 이 PR로 뭘 하려고 했는지, 왜 필요했는지 (이슈 번호가 있다면 자연스럽게 언급)
- 병합 여부와 시점 (병합 안 됐다면 억지로 성공담처럼 포장하지 말 것)
- 커밋 메시지들의 흐름(시행착오 → 해결)이 보이면 그 흐름을 실제 판단 과정으로 풀어서 설명
- 실제로 무엇을 바꿨는지 (다만 "변경된 파일 목록"을 기계적으로 나열하지 말고 이야기에 필요한 부분만)
- 기술/방식을 선택해야 했다면 왜 그렇게 판단했는지
- 이 PR을 하면서 든 생각이나 다음에 참고할 점

### 태그

이 글의 실제 내용을 잘 나타내는 구체적인 태그 3~5개 (레포지토리명 포함)

## 작성 스타일

- "이 PR은 ~했습니다", "본 PR의 목적은 ~입니다" 같은 3인칭 보고서 투는 쓰지 마세요. 대신 "~상태였다. ~를 확인해보니 ~였다. 그래서 ~로 바꿨다" 처럼, 실제로 있었던 일을 순서대로 담백하게 설명하세요.
- **"요약 → 배경 및 목적 → 구현 내용 → 기술적 의사결정 → 배운 점"처럼 뻔한 보고서 틀에 기계적으로 맞추지 마세요.** 실제로 일어난 순서를 따라 자연스럽게 이어지는 글로 쓰세요. 소제목은 필요할 때만 최소한으로 쓰고(그 글의 실제 내용을 가리키는 제목으로), 대부분은 문단으로 이어가세요. 매 글마다 "배경 및 목적", "기술적 의사결정" 같은 동일한 헤더가 반복해서 등장하면 안 됩니다.
- 코드 예시는 마크다운 코드 블록 사용
- **"허탈했다", "마음이 편해졌다", "흥미로웠다"처럼 감정을 앞세운 표현은 쓰지 마세요.** 감상문이 아니라 담백한 기술 기록입니다. 판단의 이유와 과정은 설명하되, 느낌을 전달하려 하지 마세요.
- 어려웠던 부분이나 시행착오가 있었다면 사실 그대로 담담하게 공유하세요.
- 과장되거나 상투적인 미사여구는 피하고, 딱딱한 보고서투도 지나치게 감상적인 일기투도 아닌, 담백하고 자연스러운 기술 글 톤을 유지하세요.

## 주의사항

- **제공된 데이터에는 실제 리뷰 코멘트(다른 사람이 남긴 리뷰 의견)가 없습니다.** "리뷰어가 이렇게 지적했다" 같은 코멘트나 대화를 지어내지 마세요. PR 설명(본문)과 커밋 메시지, 코드 diff에 실제로 있는 내용만 바탕으로 작성하세요.
- PR 상태가 "closed"(병합되지 않고 닫힘)라면 병합되지 못한 사실을 자연스럽게 반영하세요.

## 마크다운 형식

마크다운 형식으로 작성해주세요. **H1 제목부터 시작**하세요.

**중요 지시사항:**
- **절대로 코드 블록(```markdown)으로 출력을 감싸지 마세요**
- **절대로 frontmatter (---로 시작하는 메타데이터 블록)를 포함하지 마세요**
- **첫 줄은 반드시 H1 제목 (# {레포지토리명}: {PR_제목 또는 핵심 요약})**
- 제목 다음 첫 문단은 **순수 텍스트**로 작성 (마크다운, HTML, CSS 금지)
- 첫 문단은 한 줄 요약으로 사용됩니다
- 소제목이 필요하면 H2(##)를 쓰되, "요약"/"배경 및 목적"/"구현 내용"/"기술적 의사결정"/"배운 점 및 개선점" 같은 고정된 보고서식 라벨을 그대로 쓰지 마세요. 필요하면 그 글의 실제 흐름을 나타내는 자연스러운 소제목을 직접 지으세요.
- **글의 맨 마지막 줄에 아래 형식으로 태그를 붙이세요** (다른 곳엔 태그를 쓰지 마세요):
  `**태그:** 태그1, 태그2, 태그3`
  - '레포지토리' 필드 값(프로젝트명)을 태그에 반드시 포함하세요.
  - 나머지는 이 PR에서 실제로 다룬 기술/기능 영역 위주로 구체적으로 채우세요.
  - "개발", "PR", "코드리뷰", "본인", "학습", "커밋"처럼 모든 글에 다 붙을 법한 뭉뚱그린 단어는 피하세요.

**출력 형식 예시** (실제 글은 이 예시의 문장을 베끼지 말고, 이 정도의 담백한 흐름만 참고하세요):

# website: 피드 매직링크 토큰 + 이미지 업로드 API 구현

피드 기능에 필요한 매직링크 토큰 발급과 이미지 업로드 API를 구현한 PR이다.

...(이런 식으로 실제 판단 흐름을 따라 자연스럽게 이어감)...

**태그:** website, 매직링크, 이미지업로드

## 제공되는 데이터

JSON 데이터에는 다음 정보가 포함됩니다:
- PR_번호: PR 번호
- 제목: PR 제목
- 설명: PR 본문(작성자가 직접 쓴 설명, 이슈 링크 등)
- 상태: "merged"(병합됨) 또는 "closed"(병합 안 되고 닫힘)
- 레포지토리: 프로젝트 이름
- 브랜치: PR의 헤드 브랜치명
- 베이스_브랜치: 병합 대상 브랜치명
- 작성자: PR을 올린 사람의 GitHub 아이디
- 생성일, 병합일: 시각 정보
- PR_URL: GitHub PR 링크
- 추가_라인, 삭제_라인: 변경 규모
- 변경된_파일_목록: 수정된 파일 경로 리스트
- 변경_내용: 상위 5개 코드 파일의 상세 변경 내용 (파일명, 추가/삭제 라인 수, 패치 diff)
- 커밋_메시지_목록: 이 PR에 포함된 커밋들의 메시지 (시행착오 흐름을 파악하는 데 활용)

**중요 지시사항:**
- '설명' 필드에 이슈 번호나 배경 설명이 있다면 그 맥락을 살려서 왜 이 작업이 필요했는지 자연스럽게 풀어내세요.
- '커밋_메시지_목록'을 통해 이 PR이 어떤 순서로 진행됐는지(예: 초기 구현 → 버그 수정 → 리팩토링) 파악해서, 그 과정에서 실제로 어떤 판단을 했는지 이야기 흐름에 반영하세요.
- '변경_내용'의 패치(diff)를 분석해서 실제로 무엇이 바뀌었는지 파악하되, 파일 목록을 기계적으로 나열하지 말고 이야기에 필요한 부분만 짚으세요.

이 정보들을 활용하여, 실제로 이 PR을 작성한 사람이 자기 블로그에 쓰듯 포스팅을 작성해주세요.
