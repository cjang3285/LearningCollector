# 분산 아키텍처 설계 옵션

## 🎯 목표

**노트북/데스크탑**과 **라즈베리파이**로 역할 분리
- 노트북/데스크탑: AI Chat 파일 다운로드 감지 (항상 켜져있음)
- 라즈베리파이: DB 서버, 24시간 가동, 중앙 저장소

---

## 📊 아키텍처 옵션 비교

### 옵션 1: Thin Client (파일 전송 방식)

```
┌─────────────────────────────┐
│  노트북/데스크탑              │
│  ┌────────────────────────┐ │
│  │ AIExportWatcher        │ │
│  │ - Downloads 폴더 감시  │ │
│  │ - 파일 감지 시 전송    │ │
│  └──────────┬─────────────┘ │
└─────────────┼───────────────┘
              │
              │ 원본 마크다운 파일 전송 (scp/rsync/REST API)
              ▼
┌─────────────────────────────┐
│  라즈베리파이                │
│  ┌────────────────────────┐ │
│  │ 파일 수신              │ │
│  │   ↓                    │ │
│  │ AIMarkdownParser       │ │
│  │ - Claude/GPT/Gemini    │ │
│  │   ↓                    │ │
│  │ AIChatSaver            │ │
│  │ - PostgreSQL 저장      │ │
│  └────────────────────────┘ │
└─────────────────────────────┘
```

**장점:**
- ✅ 클라이언트가 단순 (Python 의존성 최소화)
- ✅ 파싱 로직 중앙화 (파이에서만 관리)
- ✅ 파싱 규칙 변경 시 파이만 업데이트
- ✅ 원본 파일 보존 (디버깅/재파싱 용이)

**단점:**
- ❌ 네트워크 트래픽 증가 (파일 크기만큼 전송)
- ❌ 파이 부하 증가 (파싱 작업)
- ❌ 전송 중 파일 손상 가능성

**구현 방법:**
- `scp` 또는 `rsync`로 파일 전송
- REST API 엔드포인트 (`POST /upload-ai-chat`)
- 파이에서 기존 `AIChatCollector.collect_from_files()` 재사용

### 옵션 2: Thick Client (데이터 전송 방식)

```
┌─────────────────────────────┐
│  노트북/데스크탑              │
│  ┌────────────────────────┐ │
│  │ AIExportWatcher        │ │
│  │   ↓                    │ │
│  │ AIMarkdownParser       │ │
│  │ - Claude/GPT/Gemini    │ │
│  │   ↓                    │ │
│  │ ConversationData       │ │
│  │ (구조화된 객체)        │ │
│  └──────────┬─────────────┘ │
└─────────────┼───────────────┘
              │
              │ JSON 데이터 전송 (REST API)
              │ { provider, title, messages: [...] }
              ▼
┌─────────────────────────────┐
│  라즈베리파이                │
│  ┌────────────────────────┐ │
│  │ REST API 수신          │ │
│  │   ↓                    │ │
│  │ AIChatSaver            │ │
│  │ - PostgreSQL 저장      │ │
│  └────────────────────────┘ │
└─────────────────────────────┘
```

**장점:**
- ✅ 네트워크 트래픽 감소 (구조화된 JSON만 전송)
- ✅ 파이 부하 감소 (파싱 작업 분산)
- ✅ 데이터 검증 후 전송 (파싱 실패 시 클라이언트에서 재시도)
- ✅ 오프라인 대응 가능 (로컬에 큐잉 후 나중에 전송)

**단점:**
- ❌ 클라이언트 복잡도 증가 (전체 ETL 스택 필요)
- ❌ 의존성 관리 어려움 (노트북/데스크탑마다 Python 환경)
- ❌ 파싱 로직 변경 시 모든 클라이언트 업데이트 필요
- ❌ 원본 파일 손실 (재파싱 불가)

**구현 방법:**
- 클라이언트: `parse/`, `export/` 모듈 포함
- REST API: `POST /api/v1/ai-conversations`
- 파이에서 Saver만 실행

### 옵션 3: Hybrid (선택적 파싱)

```
┌─────────────────────────────┐
│  노트북/데스크탑              │
│  ┌────────────────────────┐ │
│  │ AIExportWatcher        │ │
│  │   ↓                    │ │
│  │ [옵션 선택]            │ │
│  │ - 원본 전송 모드       │ │
│  │ - 파싱 후 전송 모드    │ │
│  └──────────┬─────────────┘ │
└─────────────┼───────────────┘
              │
              │ 설정에 따라 원본 또는 JSON 전송
              ▼
┌─────────────────────────────┐
│  라즈베리파이                │
│  ┌────────────────────────┐ │
│  │ 멀티 엔드포인트        │ │
│  │ - /upload-file         │ │
│  │ - /submit-data         │ │
│  └────────────────────────┘ │
└─────────────────────────────┘
```

**장점:**
- ✅ 유연성 (상황에 따라 선택)
- ✅ 테스트 용이 (두 방식 비교 가능)

**단점:**
- ❌ 구현 복잡도 2배
- ❌ 유지보수 부담

## 🚀 추가 고려사항

### 실행파일 패키징

**Thin Client용:**
```bash
# PyInstaller로 경량 클라이언트 빌드
pyinstaller --onefile \
  --name ai-chat-watcher \
  client/watcher.py

# 결과: ai-chat-watcher.exe (5-10MB)
# 의존성: requests, watchdog만
```

**Thick Client용:**
```bash
# 전체 ETL 스택 포함
pyinstaller --onefile \
  --name ai-chat-collector \
  client/collector.py

# 결과: ai-chat-collector.exe (30-50MB)
# 의존성: 전체 parse/ 모듈, dataclasses, 등
```

### 통신 프로토콜

**REST API 방식 (권장):**
```python
# 파이에서 FastAPI/Flask 서버 실행
# http://raspberry-pi.local:8000

POST /api/v1/upload-file      # Thin Client
POST /api/v1/ai-conversations  # Thick Client
```

**파일 전송 방식 (간단):**
```bash
# scp/rsync (별도 서버 불필요)
scp file.md pi@raspberry:/data/
```
